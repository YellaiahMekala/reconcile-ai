# PQ1.2.1: KEDA overlay run on a real kind cluster (2026-11-19)

Goal: prove `k8s/overlays/keda` on a real cluster, not only with kubeconform.

## Honest scope

- Real: kind v0.25.0 (Kubernetes v1.31.2), KEDA 2.21.1 (Helm chart 2.21.1), metrics-server v0.7.2, the unmodified base,
  the unmodified `overlays/keda` ScaledObject, KEDA's own HPA, real Prometheus-scaler HTTP calls.
- Stubbed: the app image is NOT built. The `reconcile-ai` container is replaced by a busybox httpd that answers the
  actuator probe paths. Prometheus is NOT real: a busybox httpd (`prometheus-server.monitoring.svc:80`) returns a static
  `/api/v1/query` vector whose value I edit by hand. So this proves manifests, KEDA wiring and scaling mechanics, not the
  app's real `reconcile_investigations_executor_*` metrics or behaviour under real load.
- Harness: `k8s/overlays/keda-kind-proof/` (test only; builds on `../keda`, adds a dev Secret, the stub app patch and the stub Prometheus).
- No cloud spend, no paid API. Tools (kind, helm) downloaded to a local tools dir; kubectl came with Docker Desktop.

## Setup

```
kind create cluster --name keda-proof
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --version 2.21.1 -n keda --create-namespace --wait
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.7.2/components.yaml
kubectl -n kube-system patch deployment metrics-server --type=json -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl apply -k k8s/overlays/keda-kind-proof
```

KEDA pods: `keda-operator`, `keda-operator-metrics-apiserver`, `keda-admission-webhooks` all Running; CRDs
`scaledobjects.keda.sh` etc. present.

## Bug found and fixed: ScaledObject had no namespace

First apply (before the fix):

```
deployment.apps/reconcile-ai created
Error from server (NotFound): error when creating ".": admission webhook "vscaledobject.kb.io" denied the request:
Deployment.apps "reconcile-ai" not found
```

Cause: `base/kustomization.yaml` sets `namespace: reconcile` for its own resources only. `scaledobject.yaml` is added by
the overlay, so it rendered with no namespace and `kubectl apply -k` put it in the current (default) namespace, where
there is no `reconcile-ai` Deployment. CI's schema check could not catch this. Fix: `namespace: reconcile` in
`k8s/overlays/keda/kustomization.yaml`. After the fix `kubectl kustomize` shows `namespace: reconcile` on the ScaledObject.

## ScaledObject becomes Ready

```
$ kubectl -n reconcile get scaledobject,hpa,deploy
scaledobject.keda.sh/reconcile-ai   apps/v1.Deployment  reconcile-ai  MIN 2  MAX 6  READY True  ACTIVE False  FALLBACK False  PAUSED False  TRIGGERS prometheus,cpu
horizontalpodautoscaler.autoscaling/keda-hpa-reconcile-ai  Deployment/reconcile-ai  0/3 (avg), cpu: 0%/70%  2  6  2
deployment.apps/reconcile-ai   2/2
```

- Condition: `Ready=True ScaledObjectReady "ScaledObject is defined correctly and is ready for scaling"`.
- Only `keda-hpa-reconcile-ai` exists: the base HPA `reconcile-ai` was removed by the overlay patch, as intended.
- Deployment went to 2 replicas (minReplicaCount) from the 1 it started with (base has no `replicas`).
- Admission info events: KEDA 2.21 warns `pollingInterval` and `cooldownPeriod` are "not relevant" unless
  `minReplicaCount` is 0 or `idleReplicaCount` is set. Harmless; the fields were kept and the README now says so.

## Scale up in response to the trigger

The stub's returned value is the query result (active + queued across the namespace). Target is 3 per pod (AverageValue).

| Step | Stub value | HPA target | Result |
|---|---|---|---|
| start | 0 | `0/3 (avg), cpu 0%/70%` | 2/2 |
| 04:23:44 set 12 | 12 | `6/3 (avg)` then `3/3` | 4/4 within 15 s (12 / 3 = 4) |
| 04:25:52 set 30 | 30 | `7500m/3` then `5/3` | 4/6 at +60 s, 6/6 at +75 s (capped at max 6; 10 wanted) |

Scale-up pace is not the 2-pods-per-30-s policy limit being slow: 2 to 4 happened in one step, 4 to 6 in one step.

## Prometheus down (ignoreNullValues "false")

Prometheus stub scaled to 0 while at 6/6:

```
scaledobject reconcile-ai   READY False  ACTIVE False  FALLBACK False
hpa keda-hpa-reconcile-ai   <unknown>/3 (avg), cpu: 0%/70%   REPLICAS 6
Ready=False TriggerError ; HPAActive=False FailedGetExternalMetric
KEDA log: ERROR prometheus_scaler error executing prometheus query ... Get "http://prometheus-server.monitoring.svc:80/api/v1/query?query=sum(...
```

Because 6 is also the maximum, that run alone is ambiguous. A second run at an intermediate count: Prometheus restored,
value set to 12 (wants 4). Scale-down damping: replicas stayed 6 for the 300 s window, then dropped one pod at a time
(first drop 6 to 5 at 04:34:47, about 6 min after the change). With 5/5 running, Prometheus was stopped:

```
04:34:51 prometheus-server scaled to 0
04:35:06 5/5 ready=True
04:35:37 5/5 ready=True
04:35:53 5/5 ready=False
04:36:39 5/5 ready=False      (would otherwise have dropped to 4 about 60 s after the previous drop)
04:36:55 Prometheus back -> 4/4 ready=True
```

So with the metric unavailable the replica count was held at 5 (ScaledObject Ready=False, TriggerError) and scaling
resumed when Prometheus returned. The hold lasted about 1 minute in this run; I did not test a longer outage.

## Scale down

Confirmed above: the 300 s scale-down stabilization window delayed the first reduction (6 to 5) by roughly 6 minutes, then
removal is one pod per 60 s (5 to 4 at 04:36:55 once Prometheus was back). I did not wait the full way down to min 2.

## Not proven

- The real app image and its real `reconcile_investigations_executor_active/queued` gauges, and a real Prometheus
  scraping them (label `namespace="reconcile"` in the query depends on the real scrape config).
- CPU trigger under real load (stub stayed at 0% CPU; HPA showed `cpu: 0%/70%`, i.e. metrics-server path works).
- Scale-down to the minimum of 2, and the `ignoreNullValues` hold for long outages.
